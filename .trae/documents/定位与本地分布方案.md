# 定位功能与「本地分布」接入方案

> 本文档已按「手机 App（Capacitor 原生打包）+ 设备 GPS」的澄清修订。

## Context（背景与目标）

现有 app 是纯前端 + dev 代理的植物图鉴：本地图鉴是固定 20 种植物的离线数组，网络百科走 Wikipedia + CVH 补充。项目**原本就定位为手机 App**，因此定位功能必须使用**设备 GPS**，而不是网页/IP 定位。

目标：

1. 增加定位功能（定位到某市），并由此得到所在省；
2. 以此为地基，未来实现「某省有哪些常见植物」，做成真正的本地图鉴；
3. 引入轻量后端（当前项目只有前端 + dev 代理，没有后端），使 CVH 在离线部署/原生包里也能用。

## 已确认的决策

| 项        | 决策                                                                     |
| -------- | ---------------------------------------------------------------------- |
| 定位方式     | **设备 GPS 为主** + IP 兜底 + 手动选择；权限只在用户点击「定位」时申请，不首屏自动弹窗                   |
| 交付形态     | **Capacitor 原生打包**；本机只生成脚手架与原生配置，真机构建/安装由用户执行（本机无 Android SDK / Xcode） |
| 「某省常见植物」 | 口径 = **CVH 标本聚合常见度排行**（按省统计采集记录数排序），**仅抓取一次**、抓取后入库供后续增量；**本期只做模拟数据显示**，真实 ETL / 入库留待后续 |
| 本地图鉴分流   | **按定位权限门控**：未授权 → 固定 20 种离线数组（绝不触发 IP 兜底）；已授权（含手动选择/持久化恢复）→ 该省常见植物排行 |
| 后端       | 新增轻量 Node 服务：`/api/cvh/*` 代理（补 Referer）+ 静态托管 `dist/`                  |
| 真机验证     | HTTPS 隧道（用户后续执行；隧道在此的作用是让手机上的 App 能访问到本机后端）                            |

## 实测事实（设计依据）

### 定位与地理反查

| 服务                                                                           | 实测结论                                                                                                                                                                                    |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BigDataCloud `reverse-geocode-client?latitude&longitude&localityLanguage=zh` | ✅ 免密钥、`Access-Control-Allow-Origin: *`；杭州坐标 → `principalSubdivision:"浙江省"`、`city:"杭州市"`；北京 → `"北京市"`；并附 `principalSubdivisionCode:"CN-ZJ"`。**这就是「坐标 → 中文省市」的唯一解析入口**                    |
| BigDataCloud `ip-geolocation`                                                | ❌ 403（免费额度不含 IP 查询）                                                                                                                                                                     |
| ipwho.is                                                                     | ✅ `Access-Control-Allow-Origin: *`、免密钥，返回 `latitude/longitude`、`region_code:"HA"`；但 `?lang=zh` 仍返回英文 `"Henan Sheng"/"Zhengzhou"` → **因此 IP 路径只取它的坐标，再交给 BigDataCloud 反查中文名**，避免维护英文名映射表 |
| Nominatim                                                                    | ❌ 探测无响应，放弃                                                                                                                                                                              |

### 省名归一化

CVH `distribution_c` 用短名并以 `、` 分隔（银杏实测为 `浙江、湖北、重庆、贵州、国内各省栽培`），故需把 `浙江省/内蒙古自治区/北京市` 归一为 `浙江/内蒙古/北京` 再比对，并识别「国内各省栽培 / 各省栽培 / 全国各地」这类全国栽培表述。

### 省市数据

`modood/Administrative-divisions-of-China` 的 `provinces.json`（1081 B，34 条）+ `cities.json`（19528 B，约 340 条）可获取，体量足够小，内联进仓库供手动选择。

### 其它已验证项

* **后端可用普通** **`fetch`** **补 Referer**：实测 `fetch(url,{headers:{Referer}})` → 返回数据，对照组不带 Referer → `{"message":"access denied"}`。故无需退回 `node:http`。

* **CVH 标本按省接口已打通**（`controller/spms/list.php?stateProvince[]=浙江省!`，返回 `total` 与 `canonicalName`），但数量是**采集记录**：浙江 240,763 / 北京 99,463 / 广东 394,755 / 云南 981,872 → 客户端不可行，需后端聚合（本次不做）。

### 本机构建环境（重要）

Node v22.14.0 / npm 10.9.2 ✅；**无** **`~/Library/Android/sdk`、无** **`adb`、`ANDROID_HOME`** **未设置、无 Xcode**；**无 cloudflared / ngrok / localtunnel**；有 Google Chrome。

→ 结论：本机**只能生成 Capacitor 工程与原生配置、跑 Web 构建与** **`cap sync`**，无法出 APK、无法真机验证。真机步骤需用户执行（见文末）。

## 实施方案

### 1. 轻量后端（新增 `server/index.mjs`）

零依赖，仅 `node:http` + `node:fs` + 全局 `fetch`（Node 22）。

* `GET|POST /api/cvh/*` → 转发到 `https://www.cvh.ac.cn/*`，**补** **`Referer: https://www.cvh.ac.cn/species/taxon_tree.php`**（缺 Referer 会被拒），透传 method/query/body 并流式回写。

* **响应加** **`Access-Control-Allow-Origin: *`** **并处理** **`OPTIONS`** **预检**，使打包后的 App 可从 `https://localhost` 跨域访问后端（无需 CapacitorHttp）。

* 静态托管 `dist/`（SPA fallback 到 `index.html`）。

* 端口 `process.env.PORT ?? 8787`。

`package.json` 新增：`"server": "node server/index.mjs"`。

### 2. Vite 代理（`vite.config.ts`）

把现有 `/cvh` 代理键改名 `/api/cvh`，使**开发态与后端同址**；target / changeOrigin / rewrite / Referer 不变。开发期无需启动后端即可跑通 CVH，旧功能不受影响。

### 3. API 基址（新增 `src/services/apiBase.ts`）

`export const API_BASE = import.meta.env.VITE_API_BASE ?? "/api";`
Web/开发态默认同源 `/api`；**Capacitor 构建时用** **`VITE_API_BASE=https://<后端或隧道地址>/api`** **覆盖**（原生 WebView 无法访问本机后端，必须给公网地址）。
`src/services/cvh.ts` 的 `CVH_BASE` 改为 `${API_BASE}/cvh`，链路（autocomplete → species\_info → trait\_info、pickSuggestion、cleanText、cache、失败静默）不变。

### 4. 类型（`src/types.ts`）

```ts
export type LocationSource = "gps" | "ip" | "manual";

export interface UserLocation {
  /** 省名短名，如「浙江」（与 CVH distribution_c 同口径） */
  province: string;
  /** 市名，如「杭州市」 */
  city: string;
  source: LocationSource;
  latitude?: number;
  longitude?: number;
}
```

### 5. 区域数据（新增 `src/data/regions.ts`）

由上述公开数据集内联生成 `PROVINCES: { name: string; cities: string[] }[]`，并导出一对纯函数：

* `normalizeProvince(fullName)` → 短名（去 `省/市/自治区/特别行政区`、`维吾尔/壮族/回族自治区` 等后缀）

* `matchesProvince(distribution: string, provinceShort: string)` → 按 `、,` 切分比对，命中或出现全国栽培表述即 true

这是「本地分布」判定的唯一入口，卡片与详情共用。

### 6. 取坐标策略（新增 `src/services/coords.ts`）

把「拿坐标」抽象成可替换实现，为将来换定位方案留缝（advisor 提示：iOS 内嵌 WebView 可能根本不开放 Web 定位）：

```ts
export async function getCoords(): Promise<{ latitude: number; longitude: number }>
```

* **原生路径**：`Capacitor.isNativePlatform()` 为真时，动态 `import("@capacitor/geolocation")`，先 `requestPermissions()` 再 `getCurrentPosition({ enableHighAccuracy: true, timeout: 15000, maximumAge: 0 })`

* **Web 路径**：`navigator.geolocation.getCurrentPosition`（**enableHighAccuracy: true**、超时 10–15s、配 `maximumAge`），用于开发与 PWA 场景

* 均失败 → 抛错，由上层决定走 IP 兜底

### 7. 定位 hook（新增 `src/hooks/useLocation.ts`）

**镜像** **`src/hooks/useGarden.ts`** **的持久化写法**（固定 key + 惰性读取 + 写入 effect + try/catch），key `plant-care-location`。

暴露 `{ location, status: "idle" | "locating" | "error", error, locate, setManually, clear }`。
`locate()` 流程（全程失败静默，不向 UI 抛异常）：

1. `getCoords()`（设备 GPS 优先）→ `source: "gps"`
2. 失败 → `fetch("https://ipwho.is/")` 取 `latitude/longitude` → `source: "ip"`
3. 两者都拿到坐标后，统一调 BigDataCloud `reverse-geocode-client?latitude=&longitude=&localityLanguage=zh`
4. `province = normalizeProvince(principalSubdivision)`、`city = city || principalSubdivision`（直辖市二者相同）
5. 任一步失败 → 保持原 `location`、置 `status: "error"`，提示可手动选择

### 8. Capacitor 脚手架

* 新增 devDeps/deps：`@capacitor/core`、`@capacitor/cli`、`@capacitor/android`、`@capacitor/geolocation`

* 新增 `capacitor.config.ts`：`appId`、`appName`、`webDir: "dist"`

* `npx cap add android` 生成 `android/` 工程

* 在 `android/app/src/main/AndroidManifest.xml` 声明 `ACCESS_FINE_LOCATION` 与 `ACCESS_COARSE_LOCATION`

* iOS 工程需 Xcode + CocoaPods，本机不具备 → **本次只做 Android**，iOS 留待用户环境就绪后 `npx cap add ios` 并加 `NSLocationWhenInUseUsageDescription`

### 9. 定位 UI（新增 `src/components/LocationBar.tsx`）

放在 `src/App.tsx` 的 `main` 顶部、`SearchBar` 之上。**按手机小屏设计**：

* 常态显示 `📍 杭州市 · 浙江`（无定位显示「未定位」）+ 定位来源提示（GPS/IP/手动）

* 操作：**定位**（点击才申请权限）、**选择城市**

* 省→市选择器用**底部弹层 + 原生** **`select`**（两级级联下拉在触屏上体验差），触控目标 ≥44px

* 样式对齐 `src/index.css` 既有 token（`sage-*` / `cream` / `ink` / `font-serif`），图标用 `lucide-react` 的 `MapPin`

### 10. 「本地有分布」标注

* `src/App.tsx` → `SearchResults` → `PlantCard` 逐层传 `province`（仅 2 跳，不引入 context）

* `src/components/PlantCard.tsx`：`plant.cvh && matchesProvince(plant.cvh.distribution, province)` 时，在来源标签旁加小型「本地有分布」徽章

* `src/components/PlantDetail.tsx`：在「中国植物志」区块 `dl` 内增加一行「本地分布」——有则「✅ 分布于 浙江」，无则「该省无分布记录」

## 本次追加：权限门控与「省级常见植物」

### 11. 权限门控规则（本地图鉴分流）

本地图鉴（`mode === "local"`）的内容**由定位权限决定**，而不是由网络决定：

| 状态            | 判定条件                            | 本地图鉴展示              | 是否触发 IP 兜底 |
| ------------- | ------------------------------- | ------------------- | ---------- |
| **未授权**       | 无持久化定位，且权限为 `prompt`/`denied`/未知 | **固定 20 种离线数组**（完整养护信息） | **绝不触发**  |
| **已授权**       | GPS 成功 / IP 兜底成功 / 手动选择城市 / 从持久化恢复 | 该省常见植物排行列表          | 仅授权后 GPS 失败时允许 |

要点：

* 授权态探测**不得弹窗**：Web 用 `navigator.permissions.query({ name: "geolocation" })`，原生用 `@capacitor/geolocation` 的 `checkPermissions()`；两者都拿不到时按「未知」处理，**视为未授权**（保持 20 种）。
* **只有用户点击「定位」按钮**才会真正发起 `requestPermissions()` / `getCurrentPosition`。
* 权限为 `denied` 时**不发起 IP 查询**，只提示「权限未授予，请手动选择城市」。IP 兜底仅发生在权限已授予但 GPS 取坐标失败的情况。
* 持久化定位（key `plant-care-location`）在重启后即视为已授权；**手动选择城市等效于授权**。
* 未授权时**永远显示恰好 20 种**；带关键词的搜索在两种状态下都可用，只是检索范围不同（未授权 = 20 种数组内过滤；已授权 = 该省排行列表内过滤）。

### 12. 省级常见植物（本期模拟数据）

口径已确认：**CVH 标本按省聚合的常见度排行，仅抓取一次后入库，后续再做增量**。本期**不实现 ETL 与入库**，先用**确定性生成的模拟数据**打通 UI 与数据流。

* 新增 `src/data/provinceFlora.ts`：`IS_MOCK = true` 常量 + `getProvinceFlora(provinceShort)`。
* 模拟数据**必须确定性生成**（以省名做种子的伪随机），且**覆盖全部 34 个省级行政区**，避免出现「有定位却无数据」的死路。
* 每行结构 `ProvincePlant { rank, name, scientificName, records, plant? }`：
  * 中文名命中那 20 种本地植物时，`plant` 挂载**完整 curated `Plant`**，该行可点开 `PlantDetail` 并带养护标记；
  * 其余行仅展示，**不可点击**。
* UI：`src/components/ProvinceFloraList.tsx` 渲染带序号的排行行（序号 / 中文名 / 拉丁学名 / 模拟采集记录数），标题「{省}常见植物排行」+ **「模拟数据」徽章** + 说明「待接入 CVH 标本聚合后替换」。
* 数据真实性：模拟行必须明确标注来源为模拟，不得暗示来自 CVH 真实统计；后续替换为真实聚合数据的入口就是 `getProvinceFlora`。

### 13. 本地分布徽章的关系

第 10 节的「本地有分布」徽章（基于 `plant.cvh.distribution`）是**逐种**判定，依赖 CVH 命中；第 12 节的省排行是**按省聚合**的列表。两者口径不同、互不替代：前者用于网络百科结果，后者用于已授权的本地图鉴。本次两者共存。

## 已知限制与风险

1. **GPS 只在安全上下文可用**：Web 侧要求 https 或 localhost；Capacitor 原生包默认跑在 `https://localhost`，因此打包后天然满足。⚠️ 若后端以 **http + 局域网 IP** 部署，真机上定位会直接不可用 —— 生产部署必须为 HTTPS（或用反向代理终止 TLS）。
2. **本机无法验证真机 GPS 与 APK**：无 Android SDK / Xcode / 隧道工具，第 3 层验证必须由用户完成。
3. **Capacitor 构建依赖公网后端**：原生 App 内无法跑 Node 服务，`VITE_API_BASE` 必须指向可公网访问的 HTTPS 后端，否则打包后 CVH 数据整体缺失（定位与本地分布徽章会因此只剩定位部分可用）。
4. **第三方定位服务无 SLA**：BigDataCloud（坐标反查）与 ipwho.is（IP 定位）均为免费第三方；两者都失败时只能手动选择。若真机网络访问不到这两个域名，需追加把 geo 也代理到后端（本次未做，避免过度设计）。
5. **「本地有分布」只在 CVH 命中的结果上出现**：实测室内栽培种覆盖约一半（拉丁名 9/20、中文名 7/20），虎尾兰/白掌/金钱树等无收录，这些植物不会有徽章。
6. **「某省全部植物」仍未实现**。三条路径的实测约束：

   * CVH 标本按省聚合：接口已打通，但浙江 24 万 / 广东 39 万 / 云南 98 万**条采集记录**，需后端或离线 ETL 聚合；记录数可近似「常见度」

   * 维基百科省份分类（`Category:<省>植物`）：纯前端可用但覆盖极不均——云南 1381、陕西 86、湖南 76、福建 61、四川 732、湖北 140、浙江 91、江苏 26、河南 16、山东 12、北京 6，**广东/台湾无此分类**

   * 「常见植物」本质是园艺/人文概念，采集记录数 ≠ 常见度；任一方案都需在 UI 如实标注来源与口径
7. 本次后端只做 CVH 代理 + 静态托管，**不含**按省聚合逻辑。
